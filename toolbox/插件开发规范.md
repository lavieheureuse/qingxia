# 轻匣插件开发规范

本文以轻匣 **1.0.19** 的实际实现为准，说明如何制作可以导入的插件。轻匣兼容一部分 uTools 插件结构和接口，但并不是完整的 uTools 宿主；符合文件结构也不代表依赖其他接口的插件一定能正常工作。

## 1. 可以导入什么

一个符合规范的插件是包含 `plugin.json`、插件 logo 和完整运行文件的文件夹。`plugin.json` 中的 `main` 指向本地 HTML 文件，`logo` 指向插件 logo；如果配置了 `preload`，对应文件也必须存在。入口、预加载脚本和图标必须位于插件文件夹内，不能指向外部路径。

```text
my-plugin/
├── plugin.json
├── index.html
├── app.js
├── style.css
├── preload.js       # 可选，需要 Node.js 能力时使用
└── logo.png         # 必须提供插件 logo
```

开发者可以在同一目录下添加其他图片、脚本和插件自身需要的运行时依赖。**文件夹里应当是构建完成后能直接运行的内容**，不是只包含源代码的工程。

使用者点击“添加工具”，选择该目录中的 `plugin.json`。工具箱会把插件文件复制到当前插件目录，之后打开的是复制后的文件；原目录的更改不会自动同步，需要重新导入。复制时会跳过符号链接，因此不要依赖符号链接指向的文件。

## 2. plugin.json

```json
{
  "id": "com.example.my-tool",
  "main": "index.html",
  "preload": "preload.js",
  "logo": "logo.png",
  "features": [
    {
      "code": "my-tool",
      "description": "示例工具",
      "cmds": ["示例工具", "my-tool"]
    }
  ]
}
```

| 字段 | 当前规则 |
| --- | --- |
| `id` | 建议填写稳定、全局唯一的插件标识，例如 `com.example.my-tool`。更新时保持不变；不同插件必须使用不同标识。旧插件可暂时不填写。 |
| `main` | 必填，插件内的本地入口文件。建议使用 `index.html`，不支持用开发服务器 URL 作为入口。 |
| `preload` | 可选；填写时必须是插件内存在的文件。需要 Node.js、系统能力或宿主接口时使用。 |
| `logo` | 规范要求必填；填写插件内存在的图片路径。当前轻匣尚未强制校验，缺失或路径无效时会显示默认图标。 |
| `features` | 可选。当前只读取第一个功能的信息。 |
| `features[0].code` | 用作功能标识；没有可用命令名称时也可能用作显示名称。 |
| `features[0].description` | 显示在工具列表中的说明文字。 |
| `features[0].cmds` | 第一个字符串用作工具列表名称；未找到字符串时依次回退到 `code` 和文件夹名。 |

建议始终提供一个 `features` 条目，并给 `code`、显示名称和说明填写清晰的值。当前不会根据 `cmds` 注册 uTools 搜索命令或正则触发，也不会解析 `features` 中其他功能。`pluginSetting` 等其他配置可以保留，但不能假定本工具箱会执行它们。

重新导入已添加的插件时，轻匣会提示是否更新，并保留超级面板和运行设置。两个插件都配置了 `id` 时以 `id` 识别；否则使用首个功能的 `code` 和显示名称识别，缺少 `code` 时比较完整配置文件。旧插件建议保持功能标识和显示名称稳定；需要改名时建议先设置唯一 `id`。更新成功后，轻匣会将不再使用的旧插件副本移入回收站；插件数据应保存在插件专属数据目录中。

### 插件图标

每个插件必须提供自己的 logo，工具箱的工具列表和超级面板使用该图标。将图标文件放在插件目录中，并在 `plugin.json` 的 `logo` 字段填写相对于插件目录的路径，例如 `"logo": "logo.png"`。建议使用容易辨认的正方形 PNG，并将图标文件随插件一起发布。

当前版本为兼容旧插件，没有配置 `logo`、文件不存在或路径不在插件目录内时仍可导入，并显示工具箱默认的“工”字图标；这不符合本规范。图片格式不受支持或内容损坏时，不能保证显示默认图标；发布前应实际打开工具箱确认图片正常显示。

工具箱导入时会复制插件文件。修改原工程的图标或 `plugin.json` 后，需要重新导入插件，原来的导入副本不会自动更新。

## 3. 最小示例

下面是无需预加载脚本和第三方依赖的最小插件。把以下三个代码文件和一个自备的 `logo.png` 放在同一个目录，选择其中的 `plugin.json` 导入。

`plugin.json`：

```json
{
  "main": "index.html",
  "logo": "logo.png",
  "features": [
    {
      "code": "hello",
      "description": "一个简单的示例工具",
      "cmds": ["示例工具"]
    }
  ]
}
```

`index.html`：

```html
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <meta http-equiv="Content-Security-Policy" content="default-src 'self'; script-src 'self'; style-src 'self'">
  <title>示例工具</title>
  <script src="app.js" defer></script>
</head>
<body>
  <h1>示例工具</h1>
  <button id="hello" type="button">点击试试</button>
  <p id="message" role="status"></p>
</body>
</html>
```

`app.js`：

```js
document.getElementById('hello').addEventListener('click', () => {
  document.getElementById('message').textContent = '插件已正常运行';
});
```

## 4. 运行环境和安全边界

- 当前 Windows 版本基于 Electron 31.7.7，内置 Node.js 20.18.0 和 Chromium 126。开发时仍需以目标安装包中的实际版本为准。
- 页面在独立插件窗口中以 `file://` 加载；页面脚本没有直接启用 Node.js `require`。需要系统能力时，放在 `preload` 中，通过明确的 `window` 方法向页面提供必要功能。
- 当前插件窗口的 `contextIsolation` 为 `false`，`preload` 可使用 Node.js，并能读写用户权限范围内的文件、访问网络或启动进程。**插件不是安全沙箱**；只应导入可信插件，开发者也不应向页面暴露任意文件、命令执行或网络接口。
- 建议插件页面设置适合自身功能的内容安全策略（CSP），使用本地脚本与样式，避免加载不可信的远程代码。工具箱不会统一替插件设置 CSP。
- 插件页面的非 `file:` 导航会被阻止，新建窗口请求会被拒绝。不能依赖页面跳转到外部网站或 `window.open()` 完成业务。
- 插件中的 `preload.js` 和它引用的模块应为当前宿主可执行的 CommonJS 格式；第三方依赖和原生二进制必须随插件完整提供，并兼容目标 Windows 架构和 Electron / Node 版本。工具箱不会替插件执行 `npm install`。
- 页面失去焦点时默认关闭，使用者可在插件窗口菜单中启用“独立窗口”以保持窗口。开启“后台运行”后，失焦或点击关闭按钮只会隐藏页面，插件继续运行；“随轻匣启动”可单独设置，开启后轻匣启动时会在后台加载该插件。隐藏不会触发退出回调。生命周期要求及当前实现差异见下文。

### 插件生命周期要求

“后台运行”和“随轻匣启动”是两个互不依赖的选项，每个插件单独设置：

| 场景 | 要求 |
| --- | --- |
| 轻匣启动 | 开启“随轻匣启动”的插件自动在后台启动；未开启的插件等待用户手动打开。 |
| 打开插件 | 未运行时启动插件；已在后台运行时显示现有页面，不重复启动。 |
| 点击窗口外面 | 开启“独立窗口”时保持窗口；否则按关闭插件窗口的规则处理。插件打开系统文件选择框等自身对话框时不应误关闭。 |
| 关闭插件窗口 | 未开启“后台运行”时结束插件及其负责的后台任务；开启时只隐藏页面，插件继续运行。 |
| 再次打开后台插件 | 显示原有插件页面并保持运行状态。 |
| 退出轻匣 | 所有插件的页面、后台任务和由插件负责启动的独立进程都应结束，无论是否开启“后台运行”或“随轻匣启动”。用户数据应保留。 |

插件开发者必须设计对应的资源释放逻辑，不得让插件自身启动的进程在轻匣正常退出后继续运行。若插件需要启动独立进程，还应明确记录和管理其生命周期，并避免误结束不属于该插件的进程。强制结束进程、系统崩溃或断电等异常退出不保证执行清理逻辑，插件应考虑下次启动时的恢复。

进程记录应保存在轻匣用户数据目录下的插件专属子目录中，并在停止前核实进程身份；不要仅凭进程名批量结束进程，也不要使用其他宿主（如 uTools）的进程记录。清理失败时应向轻匣返回错误，不能报告成功。

轻匣通过 `utools.onPluginExit` 等待插件主动清理资源；插件需自行注册回调并处理自己启动的进程。未注册回调的旧插件不会自动获得独立进程管理，仍需适配。清理失败时轻匣不会继续关闭插件或退出，用户可处理错误后重试。

多个插件同时退出时，若其中一个清理失败，已完成清理的插件会收到 `utools.onPluginExitCancelled` 通知，应恢复可再次操作的状态；已停止的任务不会自动重新启动。

## 5. 当前可用的宿主接口

宿主会在插件中提供 `window.utools`。只保证下表所列的当前行为；不要把未列出的 uTools 接口当作可用功能。

| 接口 | 当前行为 |
| --- | --- |
| `utools.getPath(name)` | 同步返回系统路径；支持 `userData`、`downloads`、`desktop`、`documents`、`temp`，其他名称返回空字符串。 |
| `utools.showOpenDialog(options)` | 返回 Promise；选择成功返回路径数组，取消返回 `undefined`。 |
| `utools.shellOpenPath(path)` | 返回 Promise；调用系统打开本地路径。成功通常返回空字符串，失败返回错误信息。 |
| `utools.shellShowItemInFolder(path)` | 返回 Promise；在文件管理器中定位本地文件。 |
| `utools.copyText(text)` | 写入系统剪贴板；当前不返回成功布尔值。 |
| `utools.onPluginEnter(callback)` | 在插件页面的 `DOMContentLoaded` 时调用一次，参数为 `{ code, type: 'over' }`，`code` 来自第一个功能；不提供搜索内容或 `payload`。回调需要在该事件发生前注册。 |
| `utools.onPluginExit(callback)` | 注册一个可返回 Promise 的退出清理回调；插件页面真正关闭或轻匣退出时调用，隐藏页面时不调用。回调成功后继续关闭，抛错或超时则提示并取消关闭。 |
| `utools.onPluginExitCancelled(callback)` | 轻匣退出因其他插件清理失败而取消时，通知已成功清理的插件恢复可操作状态；不会自动恢复已停止的任务。 |
| `utools.setPluginBusy(value)` | 打开管理员授权等宿主无法识别的系统对话框前设为 `true`，结束后必须设为 `false`，避免对话框使插件失焦关闭；不影响用户主动关闭或退出轻匣。 |
| `utools.setExpandHeight(height)` / `setExpendHeight(height)` | 为兼容旧代码提供，当前为空操作，不会调整窗口高度。 |

尤其注意：当前没有实现 `utools.dbStorage`、`utools.db`、`onPluginOut`、子输入框、uBrowser、`shellOpenExternal` 等接口，也没有完整的 uTools 生命周期或多功能命令分发。插件如果依赖这些能力，需要先适配或等待宿主实现；不能只凭页面打开就认定全部功能可用。

如果需要持久化数据，可由受信任的 `preload` 在 `utools.getPath('userData')` 下创建**插件专属子目录**，使用不易冲突的名称。这个 `userData` 是工具箱共享的数据根目录，默认位于 `%APPDATA%\qingxia`，不是自动按插件隔离的目录。不要把用户数据写入插件代码目录：插件重新导入或更改目录时，代码目录的位置可能改变。涉及密码、令牌等敏感数据时，必须单独设计并验证安全存储，不能把本文示例当作加密方案。

## 6. GitHub 导入

目前支持公开仓库首页地址，例如 `https://github.com/用户名/仓库名`；工具箱下载仓库默认分支的压缩包并查找插件配置，然后由用户选择和确认。暂不支持私有仓库、分支页面链接、`.upx` 安装包或自动构建源码。

要让仓库可以直接通过 GitHub 导入：

1. 仓库中提交完整的、可直接运行的插件文件，包括 `plugin.json` 指向的入口、logo、预加载脚本及其依赖。
2. 将这些文件放在仓库根目录，或根目录下不超过三级的普通子目录中。查找时会跳过名为 `node_modules`、`.git`、`dist`、`tests` 的目录，因此不要把唯一可运行插件放在这些目录中。
3. 如果使用 Vue、Vite 等构建工具，先完成构建，并将**构建产物**放入适合直接导入的目录后提交；只提交源码、而在 `public` 放置配置文件的仓库不能直接运行。
4. GitHub 导入限制压缩包不超过 100 MB、解压后不超过 500 MB，文件数量不超过 10,000；不支持符号链接及不安全的文件路径。

## 7. 发布前自查

1. 在一台没有开发环境的 Windows 电脑上，安装或运行工具箱，从干净的插件文件夹导入 `plugin.json`。
2. 确认已提供插件 logo、`plugin.json` 路径正确，工具列表和超级面板均能正常显示图标；确认工具名称、说明、主要操作和错误提示可用，打开后无白屏。
3. 分别测试默认失焦关闭、“独立窗口”、“后台运行”和“随轻匣启动”，检查关闭、隐藏、重新打开和重启轻匣后的任务与数据行为。
4. 如需保存数据，重启工具箱后确认数据仍在；测试取消文件选择、无权限、网络异常及依赖缺失等情况。
5. 如需通过 GitHub 导入，使用公开仓库地址测试完整导入过程，并在没有本机 Node.js、浏览器或其他开发工具的环境中验证插件所需依赖。
6. 检查插件是否使用了第 5 节未列出的 uTools 接口，或依赖 uTools 的完整插件市场、搜索、生命周期与数据库能力。

参考项目：`../timestamp` 是无预加载脚本的简单网页插件；`../douyin-utools` 展示了使用 `preload` 封装本地能力的方式。参考项目的业务功能、外部网络服务及第三方依赖仍需单独验证。
